**Scope:** Read-only review of the live site (www.qualfm.ie) and the repo at HEAD (`5d5947b`, last commit 17 Jul 2026, working tree clean). **No site, database or deployment changes were made.** The only file changed in the repo is `CLAUDE.md` (stack section was stale).

## 1. Verdict

**Don't rebuild. Two jobs: patch the framework now, then get the content published.**

1. **Security patch first.** `next@16.2.10` has `npm audit` advisories up to **critical** (unauthenticated RCE via the image optimizer with AVIF; several high). The fix is in the same major (16.3.6, or 16.2.11 for the "high" ones). Vercel hosting may reduce exposure, but the site leans on `next/image` everywhere, so this should not wait.
2. **The commercial gaps from July are all still open, 12 weeks after launch.** Live `/news` and `/projects` are empty shells, the sitemap has only the 8 static URLs, zero testimonials render, there is no emergency path and no insurance/H&S/ISO content. Since launch the commits went to search-engine plumbing (verification tags, IndexNow) and a favicon. I'd say plainly that this is the wrong order. The July audit projected the missing proof content as the biggest lever on enquiries, and none of it is code. It's waiting on Richard.
3. **The next decision is about people, not engineering:** who at QualFM owns the content backlog, and by when?

Composite score: **7.0/10 → still 7.0.** Technically the site is in good shape. The score is held down by an empty proof layer, unchanged since July.

## 3. Findings

Severity is my judgement of real-world impact for a small brochure site, not scanner output.

### Critical / High

| # | Finding | Evidence | Fix |
|---|---|---|---|
| **P1** | **Next.js has known critical/high advisories.** RCE in the Image Optimization API with AVIF (critical, fixed ≥16.3.3), Windows RCE (n/a on Vercel), SSRF and DoS in Server Actions, middleware bypass, cache confusion, server-function endpoint disclosure (high/moderate, fixed ≥16.2.11). | `npm audit --json`: 11 advisories via `next`; installed 16.2.10 | Upgrade to `next@16.3.6` + `eslint-config-next`, test on a preview deployment first, then promote. Then `npm audit fix` (non-breaking) for the transitive ones. Do **not** run `--force` — it proposes downgrading drizzle-kit to 0.18. |
| **P2** | **Proof content still absent** (audit C1). | Sitemap = 8 URLs; `/news` and `/projects` h2s are only "Quick links / Contact"; "testimonial" appears 0 times on `/` | Owner-led: publish ≥3 projects, ≥3 testimonials, 1 news post via `/admin`. Zero code. |
| **P3** | **No emergency/reactive path** (C2). "Reactive" appears 5× as a service word, "emergency" 0×. There is a "Call us now" button but no response-time promise, out-of-hours line or urgent CTA. | Home HTML text scan | Emergency strip + FAQ + homepage line (half-day of code once Richard supplies the real promise). |
| **P4** | **No procurement essentials** (C3). Insurance, H&S policy, ISO/accreditations appear 0× across pages. | Text scan of `/` | Credentials & Compliance page; needs documents from Richard. |
| **P5** | **Whole site depends on the DB being up, with no fallback.** `getHeroContent`, FAQ/client/notice queries have no try/catch; pages are force-dynamic; the sitemap also queries the DB. A Neon outage, cold-start timeout or quota hit returns 500 on home, services, contact and legal pages. The audit called the pages "edge-cacheable" — they aren't. | `lib/public-queries.ts` (no error handling); `dynamic = "force-dynamic"` in 6 pages; `x-vercel-cache: MISS` | Drop `force-dynamic`, use ISR with `revalidatePath` (already called in `refreshPublic()`) plus a 1-hour `revalidate` so scheduled notices still flip; wrap queries with a fall-back to `siteContent`. Speeds up every page and removes the outage mode. |

### Medium

| # | Finding | Evidence | Fix |
|---|---|---|---|
| **M1** | **Rate limiter is in-memory.** State resets per serverless instance/cold start, so the contact form (8/15 min) and magic-link limits (5/IP, 3/email) can be bypassed by spreading requests. Real risk is spam to the client's inbox and email-bombing the admin address. | `lib/auth/rate-limit.ts` (module-level `Map`) | Use a Vercel Firewall rate-limit rule (no code) or a small Neon table/Upstash. |
| **M2** | **Contact enquiries are not stored anywhere.** The only copy is one Resend email; if Resend errors (502 path), CONTACT_TO_EMAIL bounces, or the from-address is unverified (fallback is `onboarding@resend.dev`), the lead is silently lost. | `app/api/contact/route.ts` | Insert into a `contact_messages` table first, then send the email; show it in admin. Confirm `CONTACT_FROM_EMAIL` is a verified qualfm.ie sender with SPF/DKIM. |
| **M3** | **Markdown is rendered unsanitised.** `marked` output is injected via `dangerouslySetInnerHTML` on news and project pages; `marked` does not sanitise, and CSP allows inline scripts, so it wouldn't help. Only allow-listed admins can write it, so exposure is an admin account compromise or pasting hostile content — but the fix is cheap. | `news/[slug]/page.tsx:35,90`, `projects/[slug]/page.tsx:34,91` | Sanitise (e.g. `sanitize-html`) or configure `marked` to escape raw HTML. |
| **M4** | **Magic-link weaknesses.** (a) The link is consumed on `GET`, so corporate mail scanners (Outlook Safe Links, etc.) can burn it before Richard clicks — a likely cause of "the login doesn't work". (b) `consumeLoginToken` does select-then-update, so two simultaneous requests can both succeed. (c) Origin is taken from `req.url` rather than a fixed `SITE_URL`. | `lib/auth/magic.ts`, `app/api/auth/request-link/route.ts`, `verify/route.ts` | Make consume atomic (`UPDATE … WHERE used_at IS NULL RETURNING`); land on a confirm page and consume via `POST`; use a `SITE_URL` env var. |
| **M5** | **Sessions can't be revoked.** Stateless HMAC cookie, 7 days. `getSession` never re-checks `ADMIN_EMAILS`, so removing someone from the allow-list doesn't sign them out. Logout only clears the cookie. Logout cookie omits `secure`. | `lib/auth/session.ts` | Re-check `isAllowedAdmin` in `getSession`; optionally a server-side session table. |
| **M6** | **Upload validation is weak.** Trusts client-supplied `file.type` (`image/svg+xml` passes), and the extension comes from the user's filename. Files are public Blob URLs. | `lib/admin/actions.ts:44-60` | Allow-list jpeg/png/webp/avif; derive the extension from the type; cap dimensions. |
| **M7** | **Contact form is still name/email/message only** (audit M2): no phone, no enquiry type, no response-time promise on success. Tap-to-call is fine, but form leads are unqualified. | `contact-form.tsx`, `site-content.json` `contact.form` | Add phone + enquiry-type select + SLA copy. Combine with M2. |
| **M8** | **NAP (name/address/phone) inconsistent.** Schema says Portrane, Co. Dublin with geo coordinates; the visible contact address is just "Dublin, Ireland". No Google Business Profile/LinkedIn links, `sameAs` empty (audit M3). | `layout.tsx`, `site-content.json:515` | Decide the public address; create GBP; add `sameAs`. |
| **M9** | **Zero tests and no CI.** A bad push to `main` deploys straight to production. | No test files, no `.github` | Minimal GitHub Action: `npm ci`, `lint`, `tsc --noEmit`, `build`, `npm audit --omit=dev --audit-level=high`; plus a Vercel preview check. Add a smoke test for the contact route and `verifySessionToken`. |
